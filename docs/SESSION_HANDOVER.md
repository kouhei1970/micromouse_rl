# セッション引き継ぎ規約

制定: 2026-08-10（ユーザ提案）。長時間稼働したセッションは動作が重くなり、作業の途中で停止することがある。**定期的にまとめてセッションを入れ替える**運用とし、そのための引き継ぎメモを常時維持する。

**⚠️ 2026-08-15 改訂（ユーザ裁定・`docs/RESEARCH_PLAN.md` §12）**: 引き継ぎメモは**各役割 50 行以内・「現況」のみ**。過去分は書いた端から削除する（git 履歴が保存する。アーカイブファイルも作らない）。**更新の契機は「再開時・停止時・重大事象時」のみ**（下記 §2 のコミットごとの更新義務は廃止）。本改訂は本文の旧記述に優先する。

## 1. 引き継ぎメモの置き場所

各セッションは自分の現況を次のファイルに維持する（**常に最新の状態に保つ**）:

| セッション | ファイル |
|---|---|
| 教授 | `handover/professor.md` |
| 学生A（評価・古典ベースライン） | `handover/student_a.md` |
| 学生B（強化学習） | `handover/student_b.md` |

## 2. 更新の契機（いずれかに該当したら即更新）

1. **コミットしたとき**（コミット直後にメモも更新）
2. **大きな作業の区切り**（実験 1 本の完了、動画 1 本の完成、設計の確定など）
3. **教授から「まとめて」と指示されたとき**
4. **リセット（セッション入れ替え）の直前**
5. **詰まって作業を中断するとき**（ここが最重要 — 突然停止しても引き継げるように）

## 3. 書く内容（テンプレート）

```markdown
# 引き継ぎメモ: <役割名>

- 更新: YYYY-MM-DD HH:MM
- セッション開始: YYYY-MM-DD HH:MM

## 役割と担当範囲
<担当ディレクトリ、触ってよい/いけない範囲>

## いま何をしているか
<進行中のタスクと、どこまで終わったか。「実装は済んだが未検証」等の状態も>

## 未コミットの変更
<ファイル名と、それぞれ何を変えたか。中途半端な状態ならその旨>

## 直近の裁定・決定事項
<教授から受けた指示で、いま効いているもの。判断の前提>

## 詰まっている点・注意点
<エラー、原因不明の挙動、判断待ちの事項>

## 次にやること（優先順）
1. …
2. …

## 参照すべき文書
<この作業で読むべきファイルの一覧>
```

## 3-2. ⚠️ 役割を名乗る前に、その役割が空いているか確認する（2026-08-11 制定・必須）

**引き継ぎメモを読んだだけで役割を名乗ってはならない。**本規約は当初「`handover/<役割>.md` を読んだ者がその役割を継ぐ」という設計だったが、**「その役割が既に稼働中でないか」を確かめる手順が無かった**。

**実際に事故が起きた（2026-08-11）**: レート制限からの復帰時、既存の教授セッションが戻る **27 分前**に、別のセッションが起動して `handover/professor.md` を読み、**12 分間で裁定 3 件・任務 3 件を発行**した。その指示は学生A・学生B・准教授の引き継ぎメモに記録されたが、**`handover/professor.md` には一行も残らなかった**。結果、**下位 3 セッションは指示どおり動いているのに、指揮側は「そんな指示は出していない」と言う**状態が発生した。学生A は誰も承認していない指標定義を実装する寸前だった。

**発覚したのは、准教授が「正本に無い」と気づいたからである**（`CLAUDE.md` の precedence 規約が最後の防波堤として働いた）。**下位が指示どおり動いている限り、この欠陥は発覚しない。**

### 手順（役割を名乗る前に必ず行う）

1. **`ListAgents` で、同じ役割を名乗っているセッションが既に居ないか確認する**
2. 居る場合は**名乗らず、そのセッションへ照会する**（「役割が未確定です。指示をください」）
3. 居ない場合でも、**役割を名乗ったことを最初の作業として `handover/<役割>.md` の冒頭に記録**してから作業を始める（日時・セッション名・何を根拠に名乗ったか）
4. **`ListAgents` の「名前」を役割の根拠にしない。**名前は自動生成されることがあり、役割を保証しない（実際、准教授が名前から「教授が復帰した」と推定したのが分岐の起点になった）

### 裁定を発行するときの規律（教授セッション）

- **裁定には発行元と通し番号を本文に含める**（例: `[裁定 2026-08-11-03 / 発行: <セッション名>]`）
- **発行と同時に `handover/professor.md` へ書く。**メッセージだけで流すと、**発行者が落ちた時点で役割の記憶から消える**。下位には残るのに指揮側にだけ残らない、という非対称が実際に起きた
- 受け取った側は、**裁定の内容が正本（`docs/`）と食い違う場合は正本を優先し、食い違いを報告する**（`CLAUDE.md` の precedence 規約）

## 4. リセット（セッション入れ替え）の手順

1. 教授が「まとめてリセット」を指示する（または各セッションが自己申告）
2. 対象セッションが引き継ぎメモを**最新化してコミット**
3. ユーザが当該セッションを終了し、新しいセッションを起動
4. 教授が新セッションへ役割定義書を送る（引き継ぎメモの場所を明示）
5. 新セッションは `CLAUDE.md` → `docs/RESEARCH_PLAN.md` → **自分の引き継ぎメモ** の順に読んで再開

## 4-2. 再開時の呼びかけ（ユーザ向け・コピペ用）

**まず教授セッションだけを起動する**。学生は教授の指示で後から起動すればよい。

```
教授セッションとして再開します。handover/professor.md を読んで現況を把握し、
次の作業を進めてください。
```

学生セッションを起動したら、**教授セッションに一言伝えるだけ**でよい（学生側に直接指示する必要はない。教授が `/list-agents` で見つけて役割定義書を送る）:

```
学生セッションを起動しました
```

役割を指定したい場合は「学生A（評価担当）を起動しました」のように添える。

## 5. リセットの目安

- **稼働が長くなったとき**（目安 8〜12 時間、または動作が遅い・停止が増えたと感じたとき）
- **マイルストーンの区切り**（M1 完了時など）
- **担当範囲が変わるとき**

長さを厳密に守る必要はない。**「停止してから困る」より「区切りで自発的にまとめる」**方が安上がり、という考え方で運用する。
