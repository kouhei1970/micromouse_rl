# 監査 044: `mouse/obs_history.py` の意味的監査

- 実施: 准教授セッション（8 代目）・2026-08-15・教授発注（`AUDIT_042` 未確認 3）
- 再計算: `verification/audit_obs_history.py`
- 問い: **「遅れ (1,2,4,…,128) の各位置に入っている観測は、本当にその時点のものか」**

> bit 一致検証と単体テスト 8 件は学生B が通しているが、**通っていることと、
> 何かを検査していることは別**である（`AUDIT_041` §7-5 で学生B 自身が T7 について書いた通り）。
> **本監査は実装を読んだうえで、独立に書いた検査で意味の層を確かめた。**

---

## 1. 判定: **不合格 0 件。遅れの位置の意味は正しい**

**実装を読んで疑いを 5 つ立て（検査を書く前に列挙）、すべて検査した。**

| # | 疑い | 結果 |
|---|---|---|
| **H1** | 遅れの位置が 1 つずれている | **🟢 ずれていない。**遅れ 1・2・4・8・16・32・64・128 の**全 8 か所が 400/400 で一致**。現在の観測（先頭 17 要素）も 400/400 |
| **H2** | `reset` で同じ配列オブジェクトを 129 個入れている（`obs_history.py`:114-115） | **🟢 実害なし**（下記 §3） |
| **H3** | `step` でも同じ配列を積んでいる | **🟢 実害なし**（同） |
| **H4** | 立て直しを跨ぐ履歴 | **🔴 新規の所見**（§4） |
| **H5** | エピソード境界で履歴が残る | **🟢 残らない。**`reset` 直後は 8 か所すべてが最初の観測と同値 |

**空振りでないことも確かめた**: 隣接する歩の観測の差は**最小 0.182・中央値 1.136** で、
**定数観測ではない**（差が 0 なら検査は空振りする）。

**検査の作り**: 素の環境を私の記録器で包み（**返された観測を必ずコピーして記録**）、
その外側に履歴ラッパを掛けた。**記録器がコピーするので、ラッパ側が別名で汚れていれば差として現れる。**
遅れ ℓ の位置に入るべきものは**私の記録の `log[t-ℓ]`**（足りない分は `reset` の観測）として、
**ラッパの実装を参照せずに独立に決めた**。

---

## 2. 実装の読み（**なぜ正しいか**）

```python
self._depth = max(lags) + 1                    # 129
self._buf = deque(maxlen=self._depth)
# reset:  clear() → 最初の観測を 129 個 append
# step:   appendleft(obs)                      # index 0 = 現在・index k = k 歩前
# _stack: [buf[0]] + [buf[lag] for lag in lags]
```

`appendleft` は左端に積み、`maxlen` は**右端（最も古い）から捨てる**ので、
**`buf[k]` が k 歩前になる**。**足りない期間は `reset` で敷き詰めた最初の観測が残る**ので、
**エピソード開始から 128 歩未満でも 0 埋めにならない**（条文 §3-1 のとおり）。

---

## 3. H2/H3 — **実害は無いが、正しさが環境側の性質に依存している**

`reset` は**同じ配列オブジェクトを 129 個**バッファへ入れる（`obs_history.py`:114-115）。
`step` も `np.asarray(obs, dtype=np.float32)` で、**すでに float32 の ndarray ならコピーを作らない**。

**したがって、環境が観測配列を使い回して中身を書き換える実装だったら、履歴は全部同じ値に化ける。**

**実測した**:

| 検査 | 結果 |
|---|---|
| 連続 4 回の観測の `id` | **すべて異なる**（毎回新しい配列） |
| `reset` が返した配列が `step` 後に書き換わるか | **書き換わらない** |

→ **`Maze6Env` は毎回新しい配列を返すので、実害は無い。**

> **記録のみ（是正は求めない）**: **これはラッパ側の性質ではなく、環境側の性質に依存した安全である。**
> **環境が将来「観測用のバッファを使い回す」最適化を入れたら、履歴は静かに壊れる**
> （例外も出ず、次元も合ったまま、値だけが誤りになる）。
> **`obs_history.py` の `step` で 1 回コピーを取れば依存が切れる**（費用は 17 要素 × 1 回／歩）。
> **単体テスト T4 は現状の環境では通るが、この依存を守る検査にはなっていない**
> （環境が変わったときに壊れるのはラッパで、落ちるのは T4 ではない）。

## 4. 🔴 H4 — **介入群では 29.0% の歩で、履歴が立て直しを跨いでいる**（新規の所見）

**立て直し（衝突後に開始区画へ戻す）はエピソード内で起こる**ので、**履歴は連続したまま**である。
すると**跨いだ履歴は、機体がもう居ない場所の観測**を指す。

**実測データ（exp_021 の rollout・保存済みの `resp_hist`）から数えた**:

| 群 | 履歴 128 歩が立て直しを跨ぐ歩 |
|---|---|
| **対照群** | **25,655 / 240,000 = 10.7 %** |
| **介入群** | **68,867 / 237,316 = 29.0 %** |

**介入群では、およそ 3 歩に 1 歩で、方策が受け取る「短期の文脈」が瞬間移動を跨いでいる。**

**これは `obs_history.py` の誤りではない** — ラッパは条文どおり「直前 1.28 秒の観測」を渡している。
**1.28 秒の窓と、衝突で機体を飛ばす環境とを組み合わせたことの意味的な帰結**である。

**カード §8 の限界一覧（9 項目）にこの論点は無い。**

### 4-1. なぜ効きうるか（**仮説であり、実証していない**）

**介入群は立て直しが対照の 4.25 倍**である（`AUDIT_042`）。すると:

> **衝突が増える → 履歴が瞬間移動を跨ぐ割合が増える → 短期の文脈が壊れる → …**

**「短期文脈が効かなかった」の帰無には、少なくとも 3 つの原因候補がある**:

| # | 原因 | 分離の道具 |
|---|---|---|
| (A) | 短期文脈がそもそも効かない | にせ履歴群（exp_022 の設計） |
| (B) | 入力次元 9 倍の最適化難が打ち消した | 同上（次元・容量を揃える） |
| **(C)** | **履歴が立て直しを跨いで壊れていた** | **にせ履歴群では分離できない**（にせ履歴も同じ頻度で跨ぐ） |

**(C) は exp_022 の設計（にせ履歴 = 現在の観測の複製）では分離できない。**
にせ履歴群は履歴の**情報**をゼロにするので、**跨ぎの有無で差が出ない**からである。

**分離するなら別の道具が要る**（例: 立て直し時に履歴を初期化する条件、
あるいは立て直しを跨ぐ歩を除いた層別の集計）。
**本監査は道具を提案するが、採否は教授の裁定である。**
