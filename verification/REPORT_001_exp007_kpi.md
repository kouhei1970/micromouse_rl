## 3. 定義文を読んで解釈が一意に定まらなかった箇所（＝仕様の欠陥）

条文だけからは決まらず、こちらで解釈を決めた箇所を全部挙げる。**すべて §2 の記述欠陥である。**

### 3.1 (c) の分母 ―「(b) のうち…迷路の割合」

> (c) 有効最短走行率: **(b) のうち**、最短走行タイムが探索走行タイムより 10% 以上短い迷路の割合

「割合」の分母が **(b) 該当面**なのか**全迷路**なのか読めない。§2 の L0-a 実績表が `(b)=20/20, (c)=12/20` で分母が判別できないため、条文と既存記載の両方から決まらない。

**採った解釈**: 両方を計算して併記した。**評価器は「全迷路が分母」を採っている**（`c_fast_run_effective: {n:2, rate:0.1}` に対し `n_mazes:20`）。(b) が 100% でない条件では実際に食い違う（評価帯 L0-a: 10% と 11%、**大会実迷路 L0-a: 28%（5/18）と 100%（5/5）← 3.6 倍違う**）。

**指摘**: 「(b) のうち」と書きながら全迷路を分母にするのは、条文と実装が食い違っている。どちらでもよいが、**条文を実装に合わせて書き直すべき**。

### 3.2 (e) の分母 ―「その迷路での最良タイム」【値が実際に変わる】

> (e) 初回最短走行効率 ＝ **初回の最短走行タイム ÷ その迷路での最良タイム**

**評価器は解釈 B**（照合により確定: 解釈 B で不一致 0 件）。**同じ §2 の中で「最良タイム」が (d) と (e) で違う意味になっている。**

### 3.3 「10% 以上短い」の基準

「探索走行タイムより 10% 以上短い」を $(t_\text{探索}-t_\text{最短})/t_\text{探索} \ge 0.10$（基準＝探索走行タイム）と解釈した。もう一つの読み $t_\text{探索}/t_\text{最短}\ge 1.10$ とは閾値が 1.111 対 1.100 でわずかに違う。評価器も前者（`improvement_ratio` の値から確認）。**条文に基準を明記すべき。**

### 3.4 「探索走行」の定義

条文に定義がない。**「初回にゴールへ到達した走行」**と解釈した（評価器も同じ）。初回ゴール到達より前に失敗走行があった場合にそれを探索走行に数えるかは条文から決まらない。今回のデータでは初回走行が必ずゴールに到達したため差は出なかったが、**学習方策では初回走行が失敗する面が普通に出るので、いま決めておかないと後で揉める。**

### 3.5 「走行回数」に失敗走行を含めるか

§2 は「スタート区画から出発した回数」と定義しており、失敗走行も含むと読める。そう解釈した（`len(runs)`）。ゴールできた走行だけを数えた値も併記した。

### 3.6 (a) の「持ち時間内に」

記録されている走行はすべて持ち時間内なので実害はないが、**持ち時間の境界をまたいだ走行の扱い**が条文にない。

### 3.7 走行成立の 2 段階判定 ―【r1 の記述を r2 で訂正】

**r1 の記述**: 「結果 JSON の `outcome` は `goal` / `timeout` の 2 値のみで、先端は通過したが入り切らなかったケースが区別できない。実装されているか未確認。`outcome` に値を追加すべき」

**r2 の訂正**: **誤りだった。**評価器は §2 の 2 段階判定を実装しており、機体全体がゴール区画に入らなかった走行には **`outcome = "goal_not_contained"`** を付け、`run_time` を `None` にして暫定タイムを破棄し、係員回収でスタートへ戻している（`competition/evaluator.py` の該当箇所、`c6e08af`）。成績集計でも `outcome == "goal"` かつ `run_time is not None` の走行だけを完走として扱っており、条文どおりである。

r1 が「未確認」としたのは正しい態度だったが、**「値を追加すべき」という提案（旧・提案 10）は不要**であり撤回する。**234 面 934 走行**で観測された `outcome` が `goal` / `timeout` の 2 値だけだったのは、**古典ベースラインが区画中心で停止する設計のため 2 段階目で落ちる走行が 1 件も発生しなかった**からである。

**残る指摘**: 学習方策では `goal_not_contained` が実際に発生する。その際に **(a)〜(e) の定義がその走行をどう扱うかは §2 に書かれていない**（実装は「完走に数えない」で妥当だが、条文には無い）。**この点は条文に明記すべき。**

### 3.8 §2 が「4 指標」と書いている（既報告・教授が修正予定）

指標分離の節が (a)〜(d) を「4 指標」と呼んだまま (e) が後付けされ、§5 の M5 gate も「§2 の 4 指標すべてで比較」のままである。着任 1 通目で指摘済み、教授が修正すると回答。

| contest / L0-a | 1.157 | **1.289** | 0.971 | 28% |

| 帯 | 経路比（L0-a / L0-b / L0-c） | 速度比（L0-a / L0-b / L0-c） | (c)（L0-a / L0-b / L0-c） |

### 7.1 【r1 の「異常」を r2 で撤回】初回ゴール後に 2 本目を開始できなかった 6 面 — 異常ではなかった

**r1 の主張（誤り）**: 「初回ゴール到達の直後にエピソードが終了し、持ち時間を 219〜314 s 残したまま帰還も 2 本目も行われなかった面が 6 面ある。原因未確認。」

**r2 の訂正**: 評価器コード（`c6e08af`）を読んで確認した結果、**これは異常ではなく仕様どおりの挙動**である。r1 の誤りは 2 段構えだった。

1. **結果 JSON にエピソード終了時刻のフィールドが無い。**r1 は「記録されている走行の最後の `t_end`」を「エピソードが終了した時刻」として扱ったが、**両者は別物**である。走行が開いていない時間（帰還・追加探索の時間）はどの走行にも属さないため JSON に現れない。
2. **評価器がエピソードを終える条件は 4 つしかない**（`finished = True` の設置箇所を全数確認）: ①ゴール到達かつ走行数が上限、②走行が `timeout`、③衝突等で回収かつ走行数が上限、④**持ち時間切れ（`t >= time_budget`）**。当該 6 面は走行数 1・`timeout` 走行なしなので、**④以外に該当しない。すなわちこの 6 面も持ち時間 420 秒を使い切っている。**

**実際に起きていたこと**: 初回ゴール到達後、機体は E1 の追加探索と帰還を続けたが、**スタート区画へ戻って再出発するまでに持ち時間が尽きた。**そのため 2 本目の走行が一度も開かれず、`runs` に走行が 1 本しか残らなかった（走行が開いていなければ末尾の `timeout` 走行も記録されない）。

**これは §2 (b) の定義そのものである** —「帰還が間に合わず持ち時間切れになった面はここで落ちる」。**指標は設計どおり動いており、L0-a の成績を不当に低く見せてもいない。**L0-a が遅くて帰れなかったという、正しい評価である。

6 面が L0-a だけに出たことも整合的である。L0-a は 3 方式で最も遅く（最速タイム中央値が L0-c の 5〜9 倍）、初回ゴール後の追加探索と帰還だけで 200〜300 秒を要する。実際、帰還が間に合った面でも 2 本目の開始は初回ゴールの 200〜240 秒後であり（例: 評価帯 `maze_1004` は run1 が 95.87 s に終わり run2 の開始が 234.33 s）、**間に合うかどうかは連続的な問題で、6 面はその境界の向こう側だっただけ**である。大会実迷路（$D_0$ が大きい）で 5 面に集中したのも当然である。

**この誤りから得られる本当の指摘（こちらは有効）**:

- **結果 JSON にエピソード終了時刻と、走行に属さない時間の内訳（帰還・追加探索）を記録すべき。**現状では「持ち時間のどこが何に使われたか」が外部から復元できない。今回のように**別セッションが生データだけを見ると誤読する**。とくに学習方策では「走行していない時間」が長くなりうるので、記録がないと診断できない
- r1 が挙げた「否定できた仮説」の列挙（規格非適合・持ち時間切れ・走行回数上限・衝突/スタック）のうち、**「持ち時間切れ」を否定したのが誤りだった。**否定の根拠が「最後の `t_end` に余裕がある」という、検証できていない前提に依存していた。**生データに無いフィールドを暗黙に仮定してはならない**という教訓として記録する
