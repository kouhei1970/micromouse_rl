# note_027: 速度計画が斜めの直線と円弧を同じ上限で縛っていた

- 起案: 2026-08-18 夜 教授セッション（単独運用）
- 発端: **ユーザ指摘**（実機のマイクロマウス経験に基づく）

> カーブに入る時と出る時が同じ速さにしようとしたのですか。**カーブはゆっくり入って早く出るが鉄則**で、
> 斜め走行に入る前にカーブする時はゆっくりで、**斜めの直線はできる限り加速して速度を上げる**というのが
> 一般的だと思いますが。

- 状態: **確定**（コードと実測で確認済み）。設計への反映は第 2 章の走行アルゴリズムの中で行う

## 1. 何が起きていたか

経路の区分 `kinds` は **3 種類**ある。

| kind | 中身 |
|---|---|
| `straight` | 軸平行の直進 |
| **`diagonal`** | **45° の斜めの直線区間**（横偏差 $e_y$ の判定はここで行う） |
| `arc` | 接続円弧（クロソイドの標本も判定の定義を変えないため `arc` の印） |

ところが速度上限の割り当ては**次の 1 行**である。

```python
v_arr = np.where(kinds == "straight", 1e9, v_diag)
```

条件が `== "straight"` の**二分岐**しかないため、**`diagonal` と `arc` に同じ上限 $v_{\rm diag}$ が入る。**
斜めの直線が、円弧と同じ速度に縛られている。

**出所**（すべて同型）:
`experiments/exp_016_diagonal/run_016h1_diag.py:84`・`run_016c.py:108`・`run_016f0_diag.py:128`・
`run_016g_diag.py:164`、および**本番方策** `competition/baseline_slalom_diag.py:170`。

実行して確認した割り当て:

```
kind=straight  → 速度上限 1e+09
kind=diagonal  → 速度上限 0.7      ← 円弧と同じ
kind=arc       → 速度上限 0.7
```

## 2. 速度計画の機械そのものは正しい

`competition/baseline_slalom.py:494-568` の `build_speed_profile` は、
曲率依存の上限包絡 $v_{\rm ceil}[i] = \min(\text{base}[i], \sqrt{a_{\rm lat}/|\kappa[i]|})$ に対し
**後方パス（先の減速に間に合うよう手前を制限）→ 前方パス（手前からの加速で届く速度に制限）**
の 2 パスをかける、標準的な時間最適の速度包絡の作りである。

**つまり上限さえ正しく与えれば、減速と加速は自動で入る。**直すべきは上限の割り当てであって、計画の骨格ではない。

ただし次の 2 点は現状の設計として記録しておく。

- **円弧の中は一定速度**（`arc_pose_at` の曲率が $\kappa = s/R$ で弧内一定なので $v_{\rm ceil}$ も一定）。
  「ゆっくり入って速く出る」の**出る側の加速は円弧を抜けてから**始まる。
- **進入の減速と脱出の加速は同じ $a_{\rm max}$ で対称**。非対称のバイアスをかける項は実装に無い。

## 3. これが 016 系の一連に何を意味するか

🔴 **016 系は「速度水準 $v_{\rm diag}$ を上げると横偏差の上乗せが増える」を追ってきたが、
$v_{\rm diag}$ を上げると斜め直線の速度と円弧の速度が同時に上がる。**
**この 2 つを分離した測定は一度も行われていない。**

- 016-H1d 第 1 段（摩擦滑り）= 外れ、第 2 段（電圧飽和）= 外れ、016-H1e（横項の速度依存）= 外れ。
  **3 つとも「追従則の問題」として立てた容疑であり、3 つとも外れた。**
- 016-H1e で判明した「実測の減衰長は模型の 1/6〜1/7 で、是正は直線内でほぼ完了している」という事実は、
  **「上乗せは消し残りではなく、どこかで作られている」**ことを示していた。
  速度計画が斜め直線を円弧と同じに縛っている構造は、その「作られる場所」の有力な候補である。
- 016-H1e で観測された **$E_{\rm in}$ の 0.60 → 0.65 の跳び（2.5 倍・両群共通）**も、
  追従則をいじっても消えなかった。速度計画側の不連続なら整合する。

**私（教授セッション）の判断**: 016 系の失敗は容疑の選び方の問題ではなく、
**「制御の問題として見ていたが、計画の問題だった」**可能性が高い。見る場所が違っていた。

## 4. 扱い

**この発見を第 1 章として単独で追わない。**ユーザ裁定（2026-08-18 夜・note_025 §4-1）により
主戦線は**「自己位置推定して計画経路に沿わせる走行アルゴリズム」**へ移った。
速度計画の是正は**その走行アルゴリズムの一部として設計する**（区分ごとに別の是正を積むやり方を取らない）。

新アルゴリズムの速度計画が満たすべき要件として、本ノートから次を引き継ぐ。

1. **`diagonal` と `arc` を別の上限で扱う**（斜めの直線は加速させる）
2. **円弧内の一定速度をやめるか、少なくとも意識して選ぶ**（脱出側の加速を円弧の中から始めるか）
3. 上限包絡の 2 パス（後方・前方）の骨格は流用できる。作り直す必要はない
4. 🔴 **速度水準を 1 つのつまみで動かさない。**斜めの直線と円弧を独立に動かせる形にする
   （でないと、また 2 つの効果が混ざった測定になる）
